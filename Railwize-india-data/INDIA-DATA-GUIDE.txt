RAILWIZE - INDIA CATALOGUE AND EVALUATION GUIDE
================================================
Prepared: 11 October 2026
Files: LOAD-INDIA-CATALOGUE.sql and INDIA-DATA-GUIDE.txt

For a larger network, also see ADD-MAJOR-CITY-ROUTES.sql and MAJOR-CITIES-GUIDE.txt:
68 daily services, 111 station records (existing codes reused) and 414 stops,
including MMCT/CSMT -> NDLS in SL, 3A and 2A. That expansion works independently
or after this original catalogue. Its locally defined schedules are separate
from the researched snapshots below. Extra routes can change planner rankings
and examples that previously had no direct service.

1. WHAT YOU ARE LOADING
-----------------------
60 real Indian station identities, 27 trains, 165 timetable stops.
20 numbered services are based on researched Indian train timetables.
7 RW-prefixed services are fictional demonstration fixtures over real stations.
Coverage: Delhi, Uttar Pradesh, Punjab, Haryana, Chandigarh, Uttarakhand,
Jammu/Katra, Rajasthan, Madhya Pradesh, Gujarat, Mumbai and Pune.

The 20 real-service entries retain the listed source/destination, times, days and
cumulative kilometres from the linked timetable snapshot. 12955 and 12956 use
selected major stops, not every real halt. Other entries use the stops shown by
their source. Rounding can make distances in opposite directions differ slightly.
The tables below show EXACTLY what this SQL loads; omitted stations cannot be
searched as boarding/destination stations on that train in this dataset.

This is a reproducible evaluation catalogue, not a live Indian Railways feed.
All class capacities, fare parameters and RW-prefixed services are demonstration
values. They are not official rake compositions, fares or guaranteed connections.
Stations have approximate station-area latitude/longitude values in decimal
degrees. NDLS, NZM, MMCT and CSMT use the cited coordinate references; other points
are approximate demonstration locations and have not been individually surveyed.
Small-radius boundary results must not be treated as precise geographic claims.

COMPATIBILITY CHOICES
- Railwize supports 1A, 2A, 3A, 3E, EC, SL, 2S and UR. It has no CC enum.
  Shatabdi/Vande Bharat entries therefore expose EC only, although their real
  services have additional classes. CC is NOT relabelled as EC or 2S.
- Deccan Queen exposes 2S only. Unsupported CC/EV are omitted.
- RW901 deliberately includes all eight supported classes for UI testing; that
  combined composition is fictional. RW907 has just two SL berths to demonstrate
  a paid waitlist without making dozens of bookings.
- Timetables are recurring weekly patterns, not rows for specific calendar dates.
- Indian time (IST) is used throughout. Day 1 is the source departure date.
- Source arrival and destination departure are SQL NULL, not 00:00 or empty strings.
- Kilometres are cumulative from each train's source. They are not station metadata.
- Published routes, operating days and capacity are immutable in the application.
  Do not edit imported schedules/capacity in SQL after bookings have been made.

2. HOW TO IMPORT SAFELY
-----------------------
This file inserts catalogue data only. It does not create application databases,
change database credentials, alter business tables, delete records, register users,
insert payments, or manufacture bookings/emails/notifications.

Prerequisites:
1) Use MySQL 8.0. Keep your existing database backup if it contains important data.
2) Create the normal project databases using backend/Create-Databases.sql if needed.
3) Run the CURRENT train-service and schedule-service once with DDL_AUTO=update,
   or apply the project's existing schema migrations if you use validate/none.
   Confirm station coordinates, class inventory and departure_day_number exist.
4) Stop application services during the import. Both catalogue databases must be
   on the SAME MySQL server. All six affected tables must use InnoDB.
5) Use a DB account with SELECT/INSERT in both schemas, CREATE TEMPORARY TABLES,
   and CREATE ROUTINE/ALTER ROUTINE/EXECUTE in railway_train_db.

MySQL Workbench (recommended):
1) Open the connection used by the project.
2) File > Open SQL Script > choose LOAD-INDIA-CATALOGUE.sql.
3) If you changed database names, replace EVERY railway_train_db and
   railway_schedule_db occurrence with the configured names before execution.
4) Execute the WHOLE script, not only the statement under the cursor. The file
   uses DELIMITER and session-private staging tables. Keep the same connection.
5) Look for the result row IMPORT SUCCEEDED. On an empty catalogue it reports
   60 new stations, 27 new trains, 165 timetable stops. Existing reused stations
   reduce only the new_stations value. Scoped totals should be 60 / 27 / 165.
6) Restart services normally, then start the frontend and refresh the catalogue.

CMD alternative (no PowerShell script or execution-policy change is needed):
  mysql -h localhost -P 3306 -u root -p
At the mysql> prompt enter the absolute location using forward slashes:
  SOURCE C:/your/project/Railwize-india-data/LOAD-INDIA-CATALOGUE.sql;
Use your configured username/port, not necessarily root/3306. Enter the password
only when prompted. If mysql is not in PATH, launch its installed mysql.exe.

Existing data / repeated execution:
- Existing station codes are reused; names, IDs and coordinates are NOT overwritten.
  Review the reused-station report to ensure a code represents the correct place.
  If an existing station lacks coordinates, use Admin > Stations to fill them
  before the nearby-station tests. Newly added stations already have coordinates.
- If ANY of these train numbers already exists, or has an existing timetable,
  the loader stops before inserting application data. It does not silently mix
  old timetables with new capacity/fare settings. Inspect the conflict report.
- Running the file again after success is intentionally rejected without changes.
  You do not need to reload for another date: every train uses a weekly pattern.
- If it conflicts with your own trains, retain them. Use a separate fresh demo
  installation/database set, or prepare a reviewed subset with different fixture
  numbers. Do not solve a conflict by deleting booked trains or passenger records.
- Errors during loading roll back inserts across both databases. MySQL may leave
  auto-increment gaps after rollback; gaps are normal and not missing records.
- Only this script's temporary staging tables and named helper procedure are
  created/replaced/removed. Application tables and existing rows are retained.
- After an error, read Workbench's Action Output. Later SELECT counts are not proof
  of a successful load; IMPORT SUCCEEDED is the explicit success result.

Affected application tables:
  railway_train_db.stations
  railway_train_db.trains
  railway_train_db.train_seat_classes
  railway_train_db.train_operating_days
  railway_train_db.train_class_configurations
  railway_schedule_db.schedules
No new application database or table is required.

6. FARES, COACHES AND BERTHS
----------------------------
Railwize computes a fare for the selected segment, not the entire train route:
  distance = destination cumulative km - boarding cumulative km
  per passenger = max(minimum fare, base fare + rate per km * distance)
  total = per-passenger fare * passenger count
Amounts are INR, rounded to two decimals. These are project fare parameters,
not actual Indian Railways tariffs; catering, dynamic quotas and real tax rules
are not being reproduced by this dataset.

Class | Base INR | INR/km | Minimum INR | Default sample coaches x seats
SL    |    50.00 |   0.50 |      100.00 | 2 x 72 = 144
3A    |   100.00 |   1.20 |      200.00 | 2 x 72 = 144
2A    |   150.00 |   1.80 |      300.00 | 1 x 48 = 48
1A    |   250.00 |   2.80 |      500.00 | 1 x 24 = 24
3E    |    80.00 |   1.00 |      180.00 | 1 x 80 = 80
EC    |   150.00 |   1.50 |      250.00 | 1 x 56 = 56
2S    |    20.00 |   0.30 |       50.00 | 2 x 80 = 160
UR    |    10.00 |   0.20 |       30.00 | 1 x 80 = 80

Only classes declared for a train are configured. The defaults above do not mean
every real train has every class. RW901 uses small class inventories instead:
  SL 8, 3A 8, 2A 6, 1A 4, 3E 8, EC 6, 2S 6, UR 6; one coach per class.
RW907 uses only SL: one coach, two berths. All other trains use the defaults.
Capacity is per train/class/source-run date, shared across overlapping segments.

Worked examples:
- 12951, MMCT -> NDLS, 3A: 1,384 km.
  max(200, 100 + 1.20*1384) = INR 1,760.80 each; two people = INR 3,521.60.
- 12951, ST -> BRC, 3A: 392-263 = 129 km.
  max(200, 100 + 1.20*129) = INR 254.80 each.
- RW901, NZM -> AGC, SL: 188 km, INR 144.00 each.
- RW907, JAT -> SVDK, SL: 78 km; 50 + 0.50*78 = 89, so minimum INR 100 applies.
- 12123, SVJR -> PUNE, 2S: 2 km; minimum INR 50 applies.

Coach display:
SL -> S1/S2; 3A -> B1/B2; 2A -> A1; 1A -> H1; 3E -> M1;
EC -> E1; 2S -> D1/D2; UR -> GS1.
SL/3A berth positions repeat every eight:
  1 Lower, 2 Middle, 3 Upper, 4 Lower, 5 Middle, 6 Upper, 7 Side lower, 8 Side upper.
2A positions repeat every six:
  1 Lower, 2 Upper, 3 Lower, 4 Upper, 5 Side lower, 6 Side upper.
1A/3E detailed berth type remains unspecified in the current app. Do not claim it
models actual coupe/cabin allocation. UR is represented by the project's simplified
numbered-seat model, not Indian Railways' actual unreserved boarding process.

7. PICKING DEMONSTRATION DATES
------------------------------
Use D = a date seven days ahead in IST for normal scenarios. Choose a suitable
weekday where required, and keep every boarding date within two calendar months
of today. Avoid today if the train's boarding departure time has already passed.
Use fresh dates for independent scenarios to avoid earlier bookings/cancellations
affecting availability. Dates in this guide are relative so it remains reusable.

Important operating-day exceptions:
  12009 / 12010: not Sunday.
  12029 / 12030 and 22435 / 22436: not Thursday.
  RW906: source departures on Monday only.
  All other seeded services: daily.

Boarding date is when YOU board, which may be Day 2 of the train's source run.
Example: 12951 leaves MMCT Monday 17:00, reaches KOTA Tuesday 03:15 and departs
03:20. A KOTA -> NDLS passenger chooses Tuesday; source runDate is Monday.
RW906 arrives AGC Monday 23:55 and departs Tuesday 00:05. For AGC -> LJN choose
Tuesday; the Monday operating-day rule is still satisfied. Choosing Monday at
AGC would correspond to a Sunday source run and must return no RW906 option.

8. FEATURE WALKTHROUGH / EVALUATOR DEMONSTRATIONS
------------------------------------------------
Expected results assume these catalogues and no conflicting prior bookings/run
cancellations. Your additional trains may produce extra search/planner options.

A. Direct trains and comparative results
  Search MMCT -> NDLS, 3A, 2 passengers, date D: 12951, next-day arrival.
  Search MMCT -> JP, SL, date D: 12955.
  Search NDLS -> LJN, EC: 12004; NDLS -> ASR, EC on a non-Thursday: 12029.
  Search NDLS -> DDN, EC: 12017; NDLS -> KLK, EC: 12005.
  Search NDLS -> BSB, EC on a non-Thursday: 22436.
  Search NDLS -> JAT, 3A: 12425 with next-day arrival.
  Search CSMT -> PUNE, 2S: 12123. Reverse PUNE -> CSMT uses 12124.
  Search MMCT -> ST, 3A: compare 12951 and 12955 by time/fare/availability.

B. Intermediate boarding and distance-based fares
  Search ST -> BRC on 12951 in 3A; confirm the 129-km segment fare above.
  Search BRC -> JP on 12955: boarding is Day 2; the source run date is D-1.
  Load its timetable in Admin and show increasing cumulative distances.

C. A connection where no direct seeded train exists
  Search NZM -> BSB, SL, one passenger, D. Exact direct search has no train.
  Open alternatives; nearby=false, min transfer=60, max transfer=360 minutes.
  Expected: RW901 NZM 06:00 -> LJN 14:30, then RW902 LJN 16:00 -> BSB 21:00.
  Interchange=LJN; wait=90 minutes; both legs SL; first leg INR 322.00,
  second leg INR 217.50; combined illustrative fare INR 539.50 per passenger.
  Each leg is separately booked, paid and assigned its own PNR. This feature does
  not issue one protected through-ticket or guarantee a missed connection refund.

D. Reject unrealistic transfers
  In the same NZM -> BSB search, RW901 -> RW903 waits only 20 minutes and must be
  excluded. The planner's lowest configurable minimum is 30 minutes.
  RW901 -> RW904 waits 555 minutes and must be excluded with max=360.
  Raising max to 600 allows RW904 (overnight arrival) while RW903 stays excluded.
  A train being excluded as a connection does not make its own direct route invalid.

E. Connection entirely using the researched services
  LJN -> ASR, EC, depart on D when D+1 is not Thursday:
  12003 arrives NDLS at 22:25; 12029 leaves next day 07:20, arrives ASR 13:30.
  Set max transfer=600 minutes (wait=535); default 360 will correctly exclude it.
  Select nearby=false to make the same-station connection easy to explain.
  MMCT -> JAT, 3A via 12951/12425 is NOT offered: NDLS wait is 728 minutes,
  beyond even the planner's 720-minute maximum. This is expected, not missing data.

F. Nearby source AND destination
  Search CSMT -> ADI, SL, date D; enable nearby alternatives with radius 25 km.
  Expected nearby direct option: RW905 BDTS 08:00 -> SBT 15:00.
  BDTS is an alternative Mumbai departure and SBT is near Ahmedabad Junction.
  CSMT -> ADI in SL has no exact direct train in this dataset.
  Reduce radius to 1 km: this alternative should disappear.
  Nearby distances are straight-line estimates, not road distances/travel times.
  Reaching BDTS and travelling from SBT to the desired destination is up to the
  passenger; local transfers are not included in the rail fare.

G. Nearby destination using a real-service entry
  NDLS -> LKO, EC: no exact seeded train uses LKO, but nearby=true (radius 5 km)
  finds 12004 ending at LJN next door. LJN and LKO must not be treated as one code.
  With nearby=false, this nearby direct alternative disappears.

H. Nearby origin combined with a connection
  DLI -> BSB, SL, nearby=true, radius 15 km: look for NZM -> LJN -> BSB using
  RW901/RW902. The departure is NZM rather than DLI. Explain the local transfer.
  Only the four closest alternative stations per endpoint are considered; existing
  extra catalogue stations can affect which alternatives are selected. Exact source
  and destination are always retained. The planner returns at most 20 alternatives.

I. Weekly operation and midnight halt
  RW906 NZM -> AGC on next Monday: departure 21:00, arrival 23:55 Monday.
  RW906 AGC -> LJN on Tuesday: departure 00:05, arrival 06:00 Tuesday.
  Check arrivalDayNumber=1 / departureDayNumber=2 for AGC in the timetable.
  NZM -> LJN Tuesday still has RW901, but must NOT show RW906 originating Tuesday.
  Use the train-number filter or quote endpoint to inspect RW906 specifically.

J. Seats, saved passengers and normal booking
  Save two passengers in the master list. Book RW901 NZM -> LJN, SL, for them.
  Select saved passengers, complete Razorpay TEST payment within the two-minute
  hold, and inspect PNR, S1 coach, berth numbers/types, PDF, email attachment,
  notification, history, calendar download and chatbot PNR lookup.
  Test 3A and 2A separately to show B/A coaches and different berth patterns.
  Berth preference is a preference; inspect actual allocation instead of assuming
  a request guarantees a specific seat. Pay each booking before its hold expires.

K. Fast, reproducible waitlist promotion
  Use RW907 JAT -> SVDK, SL, date at least seven days away (fresh date).
  Capacity=2. Make and pay booking A for one passenger; make and pay booking B
  for one passenger. Both should confirm. Then make and pay booking C for one
  passenger with the WL option. It has no allocated berth while waitlisted.
  Cancel A through the app. After lifecycle processing C should become confirmed,
  acquire the released berth, and produce a promotion notification/email.
  A's normal confirmed cancellation has the configured cancellation deduction
  (default 20%: INR 20 fee and INR 80 refund from INR 100). Use the preview for
  actual values if you changed settings. C does not pay again on promotion.

L. Whole-booking waitlist (no partial promotion, no RAC)
  On a DIFFERENT RW901 date, pay SL bookings of 6 and 2 passengers, filling 8.
  Pay a third booking of 3 passengers as WL. Cancel the 2-passenger booking:
  only two seats free, so the whole 3-passenger WL booking must stay WL.
  Cancel the 6-passenger booking; now the entire WL booking can confirm together.
  Individual passengers inside a paid group are not independently promoted.

M. Hold expiry, failed payment and retry
  On a fresh RW907 date, hold both seats but do not pay. Wait over two minutes
  and refresh availability/history; lifecycle processing releases the hold.
  Booking status becomes expired. Starting checkout alone is not a captured payment.
  For failure email testing, use a provider-supported failed TEST payment attempt;
  merely closing a browser tab is not necessarily a payment.failed callback.
  Retry only within the active hold. A late captured payment should be reconciled
  to the existing late-payment/full-refund path rather than confirm an expired hold.

N. Automatic unpaid/paid waitlist deadlines
  Default paid-WL deadline is one hour before that passenger's boarding departure.
  For RW907 at 10:00 IST, leave a paid WL booking unpromoted and inspect around
  09:00 on its travel day; the existing scheduler should cancel/refund it fully.
  Create the WL booking BEFORE that cutoff. Do not alter your computer clock or
  booked timetable to accelerate this demonstration. This is a timed scenario,
  not something static catalogue rows can make happen instantly.

O. Operator cancellation of a dated train / full refunds

  Cancel a train run, select RW907 and its ORIGINAL SOURCE departure date.
  Preview, enter a meaningful reason and confirm cancellation.
  CNF and paid WL bookings for that run cancel with zero cancellation fee;
  captured amounts receive full test refunds. Unpaid holds have nothing to refund.
  Verify cancellation notification/email, refund-processed notification/email,
  history, reason in ticket/PDF, and removal from search for only that run date.
  Next day's service remains bookable. A repeat request must not duplicate refunds.
  Try a departed source run: cancellation should be rejected.
  For 12951 MMCT Monday -> NDLS Tuesday, select MONDAY even if a passenger boards
  KOTA on Tuesday. This operation covers every class/segment on that same source run.
  Separately booked connecting legs are not automatically cancelled/refunded.

9. NEGATIVE / BOUNDARY CHECKS
-----------------------------
Use the UI or Swagger for invalid requests; never insert corrupt SQL to test them.
- Same station: NDLS -> NDLS must fail validation.
- Passenger count 0, -1 or 7: reject. Counts 1 through 6 are supported.
- Null passenger inside a non-empty passenger list: reject.
- Past boarding date: reject. More than two calendar months ahead: reject.
- Today after a train's boarding time: no bookable quote for that departure.
- Wrong direction: 12951 NDLS -> MMCT does not exist; 12952 serves the reverse.
- Wrong class: 12951 SL and 12029 SL must not be offered.
- Wrong weekday: 12009 Sunday and 22436 Thursday must not be offered.
- Train exists but has no timetable: not bookable. Missing fares/days/capacity also
  make a train non-bookable. All imported trains intentionally have these fields.
- First arrival/destination departure fields should be disabled in the admin form;
  the API rejects a timetable with those endpoint times filled in.
- Duplicate stop code, nonconsecutive sequence, decreasing distance, arrival before
  previous departure, or mismatched train endpoints: schedule API rejects the route.
- IDs cannot be guessed across accounts: another user's private booking/profile
  or notifications must not become accessible with a passenger token.
- After source-run cancellation, booking/quote/search cannot revive that run.
- A second import must produce a conflict and preserve all business data.

11. IF A TRAIN DOES NOT SHOW UP
--------------------------------
Check in this order:
1) IMPORT SUCCEEDED was printed, not an error followed by unrelated SELECT results.
2) Your services connect to the same database names/server that you imported into.
3) Choose the STATION CODE, correct travel direction and a supported class.
4) Date is future, within the booking window, and the SOURCE run operates that day.
5) Day-2 boarding uses yesterday's source run. Check departure_day_number at midnight.
6) Train has not been cancelled on that source-run date; seats/WL cutoff allow booking.
7) For connections, both legs need the SAME requested class and the SAME interchange
   station code, with waiting time within your minimum/maximum. Cross-city station
   transfers at the interchange are not implemented by this planner.
8) For nearby options, check coordinates, radius, four-nearest-station cap and
   whether another existing station displaced a candidate. Direct search and
   the alternatives endpoint return different kinds of results.
9) Confirm discovery/gateway/train/schedule/reservation services are healthy and
   restarted after import. Check the API error/request ID rather than assuming
   an empty response always means a timetable is missing.
